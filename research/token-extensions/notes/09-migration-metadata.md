## 1. solana-program/token-wrap

Source: https://github.com/solana-program/token-wrap README (read at commit e1d8b2204d89b71053a8985778f4f54103b19d0d, 2026-09-28), Cargo.toml files, package.json.

- Program ID: `TwRapQCDhWkZRrDaHfZGuHxkZ91gHDRkyuzNqeU5MgR` (fixed on-chain address regardless of cluster).
- IDL: ./idl.json in repo. Docs & SDK guide page: https://www.solana-program.com/docs/token-wrap (egress-blocked from this session, not fetchable).
- What it does: bidirectional 1:1 wrapping between SPL Token (Tokenkeg) and Token-2022, including Token-2022-mint-to-Token-2022-mint. Wrapped mint is a PDA derived from (unwrapped mint, wrapped token program ID); wrapped mint authority is a program PDA. Backpointer PDA (derived from wrapped mint) records the original unwrapped mint.
- Instructions: CreateMint, Wrap, Unwrap, CloseStuckEscrow (handles MintCloseAuthority re-creation edge case), SyncMetadataToToken2022 (copies metadata from unwrapped mint - Metaplex or Token-2022 - into wrapped mint's TokenMetadata extension; caller must pre-fund rent), SyncMetadataToSplToken (copies metadata into a Metaplex metadata account for a wrapped SPL Token mint; wrapped_mint_authority PDA pays CPI rent, must be pre-funded).
- Escrow: unwrapped tokens sit in an escrow ATA owned by a program PDA; wrap mints an equal amount of wrapped tokens; unwrap burns wrapped tokens and releases escrow. 1:1 backing maintained via escrow.
- Wrapped-mint extensions: default `CreateMint` only supports the extensions baked into the default `MintCustomizer`, notably it ALWAYS adds `ConfidentialTransferMint` to every Token-2022 wrapped mint (no authority, no auditor, auto-approve accounts - immutable, can't be disabled). To add other extensions to the wrapped mint, a dev must fork the program and implement a custom `MintCustomizer` trait (program/src/mint_customizer) plus update CLI (`clients/cli/src/create_mint.rs`) and JS (`clients/js/src/create-mint.ts`) mint-size logic. So out of the box you don't choose extensions freely.
- Metadata for wrapped mints: not automatic — you must explicitly call SyncMetadataToToken2022 / SyncMetadataToSplToken after CreateMint; it is not done as part of CreateMint.
- Permissionless: anyone can CreateMint / Wrap / Unwrap, pays their own rent. Freeze authority of the unwrapped token, if any, is preserved on the wrapped token.
- Transfer Hook compatible (works with tokens implementing SPL Transfer Hook interface). Multisig signer support for wrap/unwrap.
- Audits (from README table):

## 2. Migration strategies (SPL Token -> Token-2022)

- **No in-place upgrade path**: Token-2022 is a *separate program* (`TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb`) from classic SPL Token / Tokenkeg (`TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`). A mint's owning program is fixed at creation; there is no instruction to reassign a mint's owner program. Confirmed by the fact that every migration path (docs, token-wrap, and general Solana dev consensus) requires a *new mint*, never mutates the old one.
- **Option A — SPL Token Wrap program**: wrap the existing (unwrapped) Tokenkeg mint 1:1 into a new Token-2022 wrapped mint via `solana-program/token-wrap`. Pros: permissionless, official Anza/solana-program tooling, preserves 1:1 backing via escrow, can sync metadata. Cons: deployment status on mainnet unverified as of 2026-09-28 (see above) — do not recommend for production until confirmed deployed and audited-build-verified on the target cluster; wrapped mint only gets the extensions in the default `MintCustomizer` (ConfidentialTransferMint) unless you fork the program; introduces indirection (holders must actively wrap/unwrap, liquidity fragments between wrapped/unwrapped versions unless the whole ecosystem moves together).
- **Option B — New Token-2022 mint + swap/airdrop/claim program**: mint a brand new Token-2022 mint with the desired extensions, then run your own migration program/flow: either (a) airdrop new tokens 1:1 to holders of the old mint (snapshot-based) and then encourage burning/locking the old mint, or (b) a claim/swap vault program where holders deposit old tokens and withdraw new ones (essentially a permissioned re-implementation of what token-wrap does generically). This is what most projects actually do — full control over extension set, but you own the security/audit burden for the swap contract and must handle liquidity migration (new LP pools, DEX listings) yourself.
- **Option C — Migration vaults / escrow contracts**: a middle ground — a vault program (could be a fork of token-wrap's escrow model, or a custom Anchor program) holds deposited old-mint tokens and mints/releases new-mint tokens, optionally with a time-locked or governance-gated cutover. Same tradeoffs as B but explicitly framed as an escrow rather than a full AMM-style swap.
- No official "SPL Token -> Token-2022 migration guide" page was found in the solana-com docs content tree (`apps/docs/content/docs/en`) as of this session's clone (2026-09-28) — grepped `tokens/` and `tokenization/` dirs for "migrat" with zero hits, and grepped the whole tree for "token-wrap"/"token.wrap" with only an unrelated hit in `references/spl-token-cli.mdx`. Medium confidence this content gap is real (full-repo grep, not just spot check) but a page could exist outside `docs/en` or be freshly added after this clone.
- Notable projects that migrated: **not found**. Web search for "project migrated SPL Token to Token-2022 2026" returned only generic explainer content (Raydium's SPL-vs-2022 docs, Bitbond guide, token-wrap README) with no named project case study. Mark UNVERIFIED / not found rather than fabricate an example.
- **SPL Token (Tokenkeg) -> p-token, SIMD-0266**: CONFIRMED, High confidence, multiple corroborating sources.
  - SIMD-0266 "Efficient Token program" (https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0266-efficient-token-program.md) replaced the *bytecode* behind the existing classic SPL Token program address (`TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`) with a new implementation called **p-token**, via a feature-gate activation at the start of **epoch 971** (per Anza's announcement, x.com/anza_xyz/status/2054549276546470100, and corroborated by Helius blog https://www.helius.dev/blog/solana-p-token and dev.to summaries).
  - The program ID is unchanged (same address, "replaced in place"). Instruction set and account layouts are unchanged — fully backward compatible / drop-in. Loader was moved to the upgradeable loader and **upgrade authority was set to None** (immutable) as part of the swap.
  - Binary shrank ~131 KB -> ~95 KB; compute-unit usage for common operations cut roughly ~95% per the Helius blog writeup (community source, Medium confidence for the specific CU number — treat as approximate).
  - Requires Agave >= v3.1.7 / Firedancer >= v0.812.30108 (from Anza's X post; Medium confidence, single-source for the exact version numbers, not cross-checked against a second primary source in this session).
  - **What changes for token developers**: nothing at the interface level — p-token is a drop-in replacement, no code changes required for apps built against classic SPL Token. It does NOT add Token-2022 extensions (no metadata, no transfer fees, etc.) — it is purely a compute-efficiency rewrite of the *same* Tokenkeg interface. It has no bearing on the "should I move to Token-2022" decision; it just makes staying on classic SPL Token cheaper in compute, which is worth noting in the skill so the "migrate" recommendation isn't over-sold as the only lever for CU cost.

## 3. Fungible metadata: Token-2022 TokenMetadata extension vs Metaplex Token Metadata program

- Both are usable on a Token-2022 mint; they solve different problems and can coexist:
  - **TokenMetadata extension** (Token-2022 native): metadata stored directly in the mint account itself as a variable-length TLV entry, referenced via the `MetadataPointer` extension (can point at the mint itself, self-contained, or at another account). Source: solana-com docs `tokens/extensions/metadata.mdx` (cloned 2026-09-28, High confidence, official docs).
    - Instructions: `InitializeTokenMetadata`, `UpdateField` (add/update `name`/`symbol`/`uri`/custom key), `RemoveKey` (custom keys only, not base fields), `UpdateAuthority` (rotate or clear to make immutable), `Emit` (returns serialized metadata via transaction return data, optionally a byte range) — matches interface source https://github.com/solana-program/token-metadata (interface@v1.0.0) and program source https://github.com/solana-program/token-2022 (program@v10.0.0).
    - **Rent top-up rule (confirmed from docs Callout)**: `TokenMetadata` is a variable-length TLV extension. `InitializeTokenMetadata`, `UpdateField`, and `RemoveKey` can resize the mint account's data, but they do **not** transfer additional lamports automatically. The mint account must hold enough lamports to stay rent-exempt for the metadata being stored; if metadata grows later (e.g. adding new custom keys), the caller must transfer additional lamports to the mint account *before* the instruction that resizes it, or the instruction fails.
    - Size limit: not a hard-coded cap in the docs I read; practically bounded by (a) the 10 KB Solana account realloc-per-instruction limit (Solana runtime-wide, not Token-2022-specific) and (b) rent-exemption cost scaling with size (this general-runtime limit is a general Solana fact, not re-verified against Token-2022 source in this session — Medium confidence).
    - No metadata program account needed; no extra rent for a separate PDA.
  - **Metaplex Token Metadata program** (`metadata.mdx` / `tokens/metaplex.mdx`, official solana-com docs, explicitly says it "can be used for standard SPL Tokens and Token-2022"): creates a PDA (`["metadata", program_id, mint]`) holding name/symbol/uri/seller-fee/creators, works identically for a Token-2022 mint as for classic SPL Token. Uses `createV1`/`mpl-token-metadata` (also has a Kit-flavored `mpl-token-metadata-kit` client per the docs code sample).
  - **Which to use — decision guide** (synthesized from docs + web search "Token-2022 TokenMetadata extension vs Metaplex Token Metadata fungible", Medium confidence overall since no single source states this as crisply as the synthesis below):
    - Use **TokenMetadata extension** when the token is Token-2022-native anyway (already using other extensions like transfer fees, transfer hook, interest-bearing, etc.), you want metadata co-located with the mint (fewer accounts, one rent payment, atomic with mint creation), and you don't need Metaplex-specific NFT features (creators array, seller-fee royalties, editions, delegates).
    - Use **Metaplex Token Metadata program** when you want maximum indexer/wallet/marketplace compatibility for something that still looks like a "classic" fungible/NFT (name/symbol/uri/creators/royalties), when downstream tooling built against `mpl-token-metadata`'s PDA convention is a hard requirement, or when you need pNFT-style programmable enforcement (not relevant to fungibles).
    - They are not mutually exclusive for a given mint (token-wrap's `SyncMetadataToToken2022` / `SyncMetadataToSplToken` exist precisely to keep both in sync across a wrap boundary), but most single-mint projects pick one as the "source of truth" and treat the other as a mirror if needed at all.
  - **Which do indexers/wallets/DAS actually read** — verified from source, High confidence:
    - **Metaplex/Helius DAS infra** (`metaplex-foundation/digital-asset-rpc-infrastructure`, cloned at commit 9c7e1b6, dated 2026-09-17): the `blockbuster` crate's `programs/token_extensions/` module explicitly imports and parses `spl_token_metadata_interface::state::TokenMetadata` and `spl_token_2022::extension::metadata_pointer::MetadataPointer` directly off the mint account (`mint.get_variable_len_extension::<TokenMetadata>()`, `mint.get_extension::<MetadataPointer>()` in `blockbuster/src/programs/token_extensions/mod.rs`). It also parses `GroupPointer`/`TokenGroup` and `GroupMemberPointer`/`TokenGroupMember` (see section 4). Separately, `program_transformers/src/token_metadata/` and `digital_asset_types/src/dao/scopes/asset.rs` (imports `mpl_token_metadata::accounts::{Edition, MasterEdition}`) handle the classic Metaplex Token Metadata program. So **the DAS/Helius indexing stack reads both** — TokenMetadata extension natively off the mint, and Metaplex Token Metadata via its own account parser — and this is the same codebase Helius's DAS API is built on (Helius DAS = a hosted deployment of this open-source stack; not independently re-verified against Helius's own closed API docs in this session, so treat "Helius DAS = this repo" as Medium confidence inference, not a direct Helius-source citation).
    - **Solana Explorer** (`solana-foundation/explorer`, cloned 2026-09-28): has a dedicated `app/components/account/TokenExtensionsCard.tsx` (renders Token-2022 extensions, including presumably MetadataPointer/TokenMetadata) and a separate `app/features/metadata/ui/MetadataCard.tsx` (generic metadata display, likely covering Metaplex Token Metadata) plus `app/features/decode-instruction-token-2022/` for instruction decoding. Confirms Explorer parses both paths; did not read the component internals line-by-line to confirm exact instruction/field coverage — High confidence on "both are parsed somewhere in Explorer," Medium confidence on completeness of that parsing.
    - **Jupiter**: token must have on-chain metadata; Jupiter's docs (per web search of docs.jup.ag / betastation.jup.ag) require it to "conform to the Metaplex Token Metadata" standard (name/symbol/logo/description) for its main verification flow. For Token-2022 specifically, a search result states "the Token Metadata standard in Token-2022 only recognizes metadata explicitly registered with a MetadataPointer extension" and expects the SPL Token Metadata interface (name/symbol/uri + optional additional keys) — Medium confidence, this is a WebSearch-engine paraphrase of Jupiter docs rather than a page I fetched directly (docs.jup.ag not fetched in this session; recommend re-verifying against https://docs.jup.ag/user-docs/launch/vrfd/token-verification and https://developers.jup.ag/docs/tokens before shipping as a hard claim). Also note Jupiter listing requires >= $500 liquidity on both sides and <= 30% price impact — unrelated to metadata format but often confused with it.
  - **Metaplex's own guidance (vendored skill)**: the vendored `metaplex-foundation/skill` submodule at `/home/user/ai-kit/.claude/skills/ext/metaplex` (commit 7af29ba4, cloned fresh in this session since the submodule was previously uninitialized) has **no Token-2022-specific guidance** — grepped the whole tree case-insensitively for "token-2022"/"token2022"/"token 2022" and got one unrelated hit in `cli-candy-machine.md`. `sdk-token-metadata.md` documents the Umi `createFungible`/`createNft`/`updateV1`/etc. API generically without mentioning which token program it targets. ## 4. Group/Member extension vs Metaplex Core collections

- Token-2022 `GroupPointer`/`TokenGroup` and `GroupMemberPointer`/`TokenGroupMember` extensions: documented at solana-com docs `tokens/extensions/group-member.mdx` (read in full). A "group" mint represents a collection; "group member" mints belong to it, referencing the group by address; both implement the `solana-program/token-group` interface. This is a mint-native alternative to a Metaplex Certified Collection.
- **No explicit Foundation recommendation found** comparing Group/Member extensions vs Metaplex Core collections. Grepped the full solana-com docs tree (`tokens/`, `tokenization/`) case-insensitively for "mpl-core"/"Metaplex Core"/"Core collection" — zero hits. The `group-member.mdx` page's own "related" links point only to `/docs/tokens/extensions/metadata` and `/docs/tokens/extensions` — no link to a Core/collections comparison page. Mark this as **UNVERIFIED / not found**: I could not confirm a Foundation-documented recommendation either way. Do not assert one in the skill; instead state the two options exist (Token-2022 Group/Member extensions for mint-native collections that work uniformly across the Token-2022 extension ecosystem and indexers that already parse Token-2022 extensions; Metaplex Core for the NFT-centric feature set — plugins, cheaper single-account NFT accounts, royalty enforcement, broader current NFT-marketplace support) and flag that no authoritative "use X" guidance was located as of 2026-09-28.
- The DAS/Helius indexing stack (section 3) confirms Group/GroupMember extensions ARE parsed (`blockbuster/src/programs/token_extensions/mod.rs` imports `spl_token_group_interface::state::{TokenGroup, TokenGroupMember}` and `group_member_pointer::GroupMemberPointer`, `group_pointer::GroupPointer`), so indexer support is not a blocker for either choice — High confidence.
