# Use with Codex, Grok Build and other agents

The kit's skills are [Agent Skills](https://agentskills.io) folders, which most coding agents load. Pick the install by where your agent looks — and read the last column before you rely on a tier: only Claude Code enforces one.

| Agent | Install | It reads | Enforces the [firewall tier](../README.md#firewall-tiers)? |
|-------|---------|----------|-----------------------------|
| Claude Code | `install.sh` (default) | `CLAUDE.md`, `.claude/` (skills, agents, commands, hooks), `.claude/security.json`, `.mcp.json` | **Yes.** Permission rules, sandbox and hooks all apply, so the tier is what it says it is |
| Claude Code | plugin marketplace | the plugin's agents, commands, skills, `.mcp.json` and `hooks/hooks.json` | **No tier at all.** A plugin's `plugin.json` `settings` object honors only `agent` and `subagentStatusLine`; `permissions` and `sandbox` keys are dropped at load. You get the hooks — the mainnet, secrets, on-chain and fetch-and-execute gates — and nothing else. There is no file fence, no sandbox, no egress denylist. The hooks' tier-invariant gates do work here, `solana-keygen new --force` over your default wallet included, but every **tier-varying** one reads the tier out of `.claude/security.json`, which a plugin install does not have: `kit_tier` then falls back to Relaxed, so a publish asks while force push, `gh pr merge` and the High history-rewrite prompt stay silent. The git transport overrides, `gh issue delete`, `gh repo delete`, the `git config alias.<name>` deny and the `git --config-env`, `git reflog delete` and `git reflog drop` denies are deny *rules*, so they do not apply here at all; nor does High's fence over `.git/config` and `.git/hooks/`. Three git gates reach a plugin install anyway, because they are hooks and tier-invariant: the `git config` code-executing keys (`alias.*`, `core.pager`, `core.hooksPath` and the rest, in any case spelling) are denied, and so are a destructive subcommand and a `-c` or `--config-env` reached behind another git-level option. The last two invert here and it is worth knowing: those passes fire only on the prefixed spelling, because in a full install the unprefixed one is already denied by a rule, so in a plugin install `git --no-pager clean -fd` and `git -P -c core.pager=x log` are blocked while plain `git clean -fd` and `git -c core.pager=x log` are not. Nothing is lost by it — with no deny rules and no sandbox, destructive git is broadly open in a plugin install either way — but do not read the one denial as cover for the other. The hooks do gate `context-mode`'s MCP tools here as well, but only the pattern half: the Medium/High tool-name denies need a `permissions` block — which is also why Playwright's `browser_run_code_unsafe`, `browser_network_request` and `browser_evaluate` are ungated in a plugin install at every tier, the hooks' matcher never having covered that server — and the MCP egress check reads its domain list out of `settings.json`, so with neither file present it has nothing to match and stays silent |
| Grok Build | default (`--agents` works too) | Claude Code's files, plus `AGENTS.md` and `.agents/skills/`, once you trust the folder (`/hooks-trust` or `grok --trust`) | **Hooks only, and only partly.** It reads `.claude/settings.json` for hooks and maps Claude's tool names, but sends camelCase `toolInput` and is **fail-open on malformed hook output** — a hook written for Claude Code's payload silently permits there. The kit's hooks now read both shapes. A default install does ship `.claude/security.json`, so the tier-varying hook gates — the publish ladder, force push, `gh pr merge`, the High history-rewrite prompt — do resolve the right tier here, unlike a plugin install. Permission rules and the sandbox are Claude Code's and do not apply |
| Codex | `--agents` | `AGENTS.md` and `.agents/skills/` | **No.** Even with hooks wired up, its PreToolUse coverage is `Bash`, `exec_command` and `apply_patch` — there is **no `Read` tool**, so file reads cannot be gated at all. Codex's own docs call hooks "a useful guardrail, not a complete enforcement boundary" |
| Cursor, GitHub Copilot, Gemini CLI, opencode and other Agent Skills clients | `--agents` | `AGENTS.md` and `.agents/skills/` | **No.** Instructions only: no hooks, no permission rules, no sandbox. The house rules are a request, not a boundary |

Grok Build caveats, per the [Grok Build docs](https://docs.x.ai/build/features/project-rules):

- Grok skips instruction files that `.gitignore` lists. That is why neither install mode puts its instruction file in the kit's `.gitignore` block — `CLAUDE.md` in a default install, `AGENTS.md` in an `--agents` one — and why `/update` and a re-install take it out of the block an older install wrote. Skills and commands load either way: the same block ignores `.agents/`, and Grok still registers the skills under it. Confirmed against grok 1.0.62 in CI: with `AGENTS.md` gitignored, `grok inspect` reported `projectInstructions: []` while registering the skills, and CI now asserts the installed `AGENTS.md` is not ignored before checking that Grok loads it.
- Grok sends [hooks](https://docs.x.ai/build/features/hooks) camelCase JSON (`toolInput`) where Claude Code sends `tool_input`. The kit's hooks read both, so the secret-read, pre-commit and mainnet-deploy gates in `.claude/settings.json` do fire under Grok — but Grok is fail-open on malformed hook output, so a hook that errors permits rather than blocks, and no permission rule or sandbox entry applies at all. The project `CLAUDE.md` still tells agents on other runtimes to get an explicit go-ahead before any mainnet step.
- `grok inspect` (add `--json`) prints the instruction files, skills, hooks and MCP servers Grok resolved for the current directory, without starting a session or signing in — the quickest way to see whether an install landed. In a folder you have not trusted it reports no project instructions and no project skills and still exits 0, so check the `Project trusted` line before believing an empty result.
- Under `--agents`, Grok gets no hooks at all: it reads them only from `.claude/settings.json`, and an `--agents` install writes no settings file (below).

**An `--agents` install ships no `settings.json`.** Nor `security.json`, `bin/firewall.sh` or `/firewall`. Permission rules, the sandbox flag and the `hooks` block are Claude Code's format, and nothing that reads `.agents/` parses them — Codex's prompt carries no settings path at all, and Grok takes hooks from `.claude/` only — so a copy there would be policy nobody enforces that reads as if it were in force. Installs made before this change wrote one (22,289 bytes: `sandbox.enabled: true`, 213 deny and 165 allow rules); `/update` and a re-install delete it, and leave it alone only when `.agents/` is a symlink to `.claude/`, where the file is Claude Code's live one. The kit's guard scripts still land in `.agents/hooks/`; wiring them into Codex's `.codex/hooks.json` is up to you, with the coverage limits in the table.

**A regular and an `--agents` install side by side** work, and converge to the same files whichever runs first. Only one side is governed: `.claude/settings.json`'s rules, sandbox and hooks bind Claude Code sessions, and a Codex or opencode session in the same project runs against the same repo, keys and clusters under none of them. `/doctor` names this when it finds both.

**Codex fits about 45 project skills.** It splits one shared description budget (about 22,000 characters) evenly across every skill it registers, its own built-ins and your user-level skills included, and cuts each description to its share without a marker; far enough past that it lists bare names and then drops skills, so it cannot route to them ([#212](https://github.com/solanabr/ai-kit/issues/212)). The count is of `SKILL.md` files, not packs: a default install registers 8, the four packs `helius`, `solana-mobile`, `light-protocol` and `jupiter` together bring it to 42 with every description whole, and `sendai` alone ships 49, which takes an install to 57 with 11 cut. `skills.sh add`, `/update` and `install.sh --agents` warn once an `--agents` install passes 45; remove an extension by deleting its line from `.agents/skills/extensions.txt` and running `bash .agents/bin/skills.sh prune`. CI installs the 42-skill set and the `sendai` one and fails if Codex cuts a description in the first. opencode has no budget and truncates nothing, so every description it finds is carried in every session, and nothing warns about that cost.

CI pins Codex and Grok Build and gates every change on both discovering an `--agents` install (`agents-mode-clients` in `.github/workflows/ci.yml`). The other clients in the table read the same `AGENTS.md` and `.agents/skills/`; nothing here is pinned to prove it on each commit.

Gemini CLI reads `GEMINI.md` unless you add `AGENTS.md` to `context.fileName` in its `settings.json`.

The `--agents` install command and what it rewrites are in [install.md](install.md#codex-opencode-and-other-agents).
