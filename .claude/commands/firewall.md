Show or change the agentic firewall tier. `off`, `relaxed` (default), `medium`, `high`.

**A switch takes effect in the next session.** Permission rules are read once, at session start, so editing `.claude/security.json` mid-session does not loosen — or tighten — the session you are in: the rules it started with stay in force until Claude Code restarts. Say this when you report a switch; do not imply the new tier is live.

## Show — bare `/firewall`

```bash
bash .claude/bin/firewall.sh show
```

Report the declared tier, the enforced tier, whether they agree, and the recorded rule count. Read the count from the script rather than tallying `settings.json` by hand: `enforced.ruleIds` records every list a tier generates, in `sandbox` as well as in `permissions`, and counting one half reports the other half as missing — on this repo, tallying `permissions` alone sees 439 of the 607 recorded rules and calls the other 168 absent. `absent` above zero is the real signal that the file lost rules the last apply wrote; the script names the fix. For local overrides, the sandbox state and the plugin case, run `/doctor` (check 9).

## Switch — `/firewall <tier>`

1. `bash .claude/bin/firewall.sh apply <tier>` — it records the tier in `.claude/security.json` and replaces the generated `permissions` + `sandbox` block in `.claude/settings.json` wholesale.
2. If the script takes no tier argument, set it first, then apply with no argument:
   ```bash
   python3 -c "import json;p='.claude/security.json';d=json.load(open(p));d.setdefault('declared',{})['tier']='<tier>';json.dump(d,open(p,'w'),indent=2)"
   bash .claude/bin/firewall.sh apply
   ```
   Write it through Bash, not the Edit tool: at `high`, `Edit(/.claude/security.json)` is denied so an agent cannot rewrite its own policy. The Bash form works at every tier.
3. Report the script's change list (rules added, rules removed) and any `note:` lines, and tell the user to restart Claude Code.

## Guardrails

- Only `firewall.sh apply` owns the generated block. Never hand-merge rules into `.claude/settings.json`: the block is replaced on the next apply, and permission lists merge without an un-deny primitive, so a hand-added deny cannot be lifted later.
- `high` is the only tier that denies the agent edits to `.claude/settings.json`, `.claude/security.json`, `.mcp.json` and the user-scope config under `~/.claude/`; `off`, `relaxed` and `medium` allow them, because customizing your own installation is the user's call. Say this when switching **down** from `high`, and name what it opens — and what it does not: `.claude/hooks/**` and `~/.claude/hooks/**` are denied at **every** tier, Off included, because those are the executable scripts implementing the mainnet, secrets and on-chain gates, and `/firewall` changes every tier knob without touching them. Below `high` the user owns their `.claude/` configuration, not the guards. A nested `claude` started with a policy-weakening flag (`--dangerously-skip-permissions`, `--settings`, `--permission-mode` and the like), managed settings and `.safe-ai-skill/**` are also denied at every tier.
- `off` disables the sandbox and generates no rules. Switch to it only on the user's explicit ask, and say what it turns off.
- `maintainer` is not a user tier: it is for a checkout of the solana-ai-kit repository itself, and `firewall.sh` refuses it anywhere else. It is Relaxed minus three denies — `Edit(/.claude/hooks/**)`, `Bash(claude mcp add*)`, `Edit(/.safe-ai-skill/**)` — plus `git submodule *` excluded from the sandbox so the packs can be initialized. Never suggest it for a project, and never switch to it unless the user asks by name while working on the kit. When it is in force, say what it opens: the agent can rewrite the guard hooks and the safe-ai-skill policy, and run `claude mcp add`. A nested `claude` with a policy-weakening flag stays denied, as at every tier. Remind them to return with `/firewall relaxed` before committing — `validate.sh` fails on a committed maintainer tier.
- Headless (`claude -p`, the Agent SDK, CI, or `KIT_FIREWALL_HEADLESS=1`), a hook's prompt goes silent at `relaxed`, `medium` and `high` and the command runs; only denies hold. Below `high`, mainnet writes and writes to a cluster the on-chain hook cannot identify are denied unless `CONFIRM_MAINNET=1`; `high` denies them outright. `relaxed`'s publish is denied unless `CONFIRM_PUBLISH=1`. Interactive sessions still get prompts for all three. `high`'s two ask rules fail a headless run, so CI runs `relaxed` or `off`.
- The kit cannot enforce egress at any tier: the network allowlist has no effect from project settings, and a local MCP server runs outside the sandbox entirely. State that rather than implying `high` closes egress.
- `medium` and `high` also deny `context-mode`'s `ctx_execute`, `ctx_execute_file`, `ctx_batch_execute`, `ctx_fetch_and_index` and `ctx_index` by name, because it is a default server with a code executor and no sandbox under it. Mention this when switching up to either: the context-compression tools (`ctx_search`, `ctx_stats`, `ctx_doctor`) keep working, running code through it does not. At `off` and `relaxed` every tool stays callable and the four guard hooks gate its payloads instead.
- `high` alone also denies the file tools (Edit, Write, NotebookEdit) a repository's `.git/config` and `.git/hooks/`, both of which make git run a program later. Say so when switching to `high`: git itself keeps working, and Claude Code's own sandbox already refuses shell writes to those two paths at every tier that runs it. In a linked worktree, re-apply the tier inside the worktree so the common git directory's copies are covered by absolute path too.
- `high` alone also asks before a workflow starts and before a command is retried outside the sandbox (`ASK_HIGH`), the only `permissions.ask` entries any tier emits. Say so when switching to `high`: every workflow now waits for the user's approval, and so does a command the sandbox blocked when Claude retries it outside, even under bypass mode. A command line led by an excluded command still leaves the sandbox without asking.
- `high` alone also denies `mcp__cloudflare__execute`, if the user has attached the opt-in Cloudflare server. Say so when switching to `high`: `docs` and `search` keep working, so documentation lookup is unaffected, but deploying a Worker or editing DNS through the agent is not. `medium` leaves it callable on purpose — Cloudflare is opt-in behind a token the user scoped, so attaching it is their decision, whereas `context-mode` is a default they never chose. Below `high` nothing gates it, hooks included, so the token's scopes are the boundary.
- `medium` and `high` also deny Playwright's `browser_run_code_unsafe` (arbitrary code in the Playwright process) and `browser_network_request` (arbitrary HTTP, so the `deniedDomains` list has nothing behind it), and `high` alone also denies `browser_evaluate` (arbitrary JavaScript in the page). Say what survives when switching up: `browser_navigate`, `browser_snapshot`, clicking and typing all keep working, which is what `/test-ts` and `/product-review` drive. `medium` keeps `browser_evaluate` on purpose — reading state out of a running dApp is ordinary testing, and a snapshot does not always carry the value.
- `medium` denies writes to the project's `.env`, `.env.local`, `.env.*.local` and per-environment dotenv files, and `high` denies reads of them instead. Say so when switching: at `high` a sandboxed build that loads `.env` (`npm run build`, `next dev`, `vitest`) cannot read it, `env-keys.sh` answers `HELPER_UNAVAILABLE`, and only a shell append such as `/setup-mcp`'s still writes the file. On Linux and WSL2, `medium` stops the file tools and redirects but not a shell write such as `python3 -c`. safe-ai-skill, when on, denies the reads at every tier anyway. Switching back down lifts both.
- Four groups of `Bash` denies vary by tier, all at `medium` and `high`: `gh api` — the raw API escape hatch that reaches every write endpoint, including the `gh repo delete` and `gh secret set` routes their narrower denies cover; `kill -9`, `pkill` and `killall`; `docker rm`, `rmi`, `system prune`, `volume rm` and `compose down -v`; and `bash -c`. Say so when switching up: `gh pr`, `gh issue`, `gh repo view` and `gh run` are still allowed, `relaxed` allows the kills and container removal, which are everyday work there, and the `bash -c` rule stops a skill whose set-up line runs `bash -c`, memsearch's recall among them. Switching back down lifts all four; the agent's own `bash -c` stays refused at every tier by the secrets guard, and at `off` and `relaxed` a skill's set-up line may run `bash -c`.
- `medium` and `high` also deny reading `gh`'s host file, `~/.config/gh/hosts.yml`, which `off` and `relaxed` leave readable so `gh` can start inside the sandbox. Say so when switching up: inside the sandbox `gh` can then no longer read its configuration, so only `gh pr`, `gh run` and `gh issue`, which run outside it, reach GitHub. When switching down, say what it opens: at `relaxed` that file, and any token in it, is readable by every process the agent runs; the Read and Grep tools stay refused it at every tier. The wallet and every other credential file stay denied at every tier.
